# 비동기·동기 비교 기록 (초안)

**상태: 아래 수치는 모두 시험 서버 결과이고 실제 PLC 결과가 아니다.** PLC 시험 뒤 `[PLC]` 칸을 채우고, 결론이 달라지면 고친다.

비교 조건: 같은 `plc_config.json`(timeout 2초, retries 0, 감시 1초), 같은 입력 순서, 같은 판단 코드(`Monitor`). 로그는 `logs/local_server/`의 `plc-async-20261105-174542-410435`, `plc-sync-20261105-174552-773755`이다. 키 입력 시각은 도구가 프로그램 밖에서 기록했다(`*.presses.json`).

이 비교는 **단일 실행 흐름에서 동기 통신을 쓰는 조건**에 대한 것이다. 동기 통신을 쓰는 모든 프로그램의 한계가 아니다.

## 1. 응답 대기 중 어떤 차이가 있었는가?

국번 2 읽기(무응답, 약 2.00초 대기)가 시작된 직후 입력했을 때의 결과다.

| 입력 | 판 | 입력 시도 | 키를 읽은 시각 | 지연 | 프로그램 반응 |
| --- | --- | --- | --- | --- | --- |
| `status` | 비동기 | 17:45:43.578 | 17:45:43.619 | 0.041초 | 43.621 상태 표시 |
| `status` | 동기 | 17:45:54.066 | 17:45:56.048 | 1.982초 | 56.053 상태 표시 |
| `write 300` | 비동기 | 17:45:45.586 | 17:45:45.616 | 0.030초 | 45.621 접수 |
| `write 300` | 동기 | 17:45:56.090 | 17:45:58.060 | 1.970초 | 58.068 접수 |

| 측정 | 비동기 | 동기 | [PLC] 비동기 | [PLC] 동기 |
| --- | --- | --- | --- | --- |
| 입력을 시도한 무응답 대기 1회 동안 처리한 키 | 7~10 | 0 | 미확인 | 미확인 |
| 무응답 대기 1회 동안 표시 갱신 | 3~4 | 0 | 미확인 | 미확인 |
| 표시 최대 간격 | 0.523초 | 2.222초 | 미확인 | 미확인 |

동기판의 지연은 입력 뒤 남은 대기 시간과 거의 같다. 키는 사라지지 않고 쌓여 있다가 통신 함수가 반환된 직후 순서대로 처리됐다.

**두 판이 같았던 점:** 두 판 모두 새 값을 읽지 못한 동안 마지막 정상 관측(값 200, 국번 1)을 유지했고, 실패를 값으로 표시하지 않았다.

**비동기로도 빨라지지 않은 점:** 비동기판은 `write 300`을 0.04초 만에 **접수**했지만, 실제 **전송**은 진행 중인 읽기가 끝난 뒤였다. 같은 연결의 요청은 한 번에 하나씩이기 때문이다. 비동기판이 줄인 것은 통신 시간이 아니라, 통신을 기다리는 동안 다른 처리가 멈추는 시간이다.

## 2. 동기판의 어느 처리가 다른 일을 기다리게 했는가?

- **통신 응답 대기가 원인이었다.** `read_holding_registers`와 `write_register`는 응답이나 timeout 전에 반환하지 않는다. 로그에서 `comm_start`와 `comm_end` 사이에 다른 기록이 하나도 없다.
- **사용자 입력 대기는 원인이 아니었다.** 입력은 `msvcrt.kbhit()`로 확인만 하고 바로 넘어가므로 사용자가 입력하지 않아도 감시는 계속됐다. 차단형 `input()`을 썼다면 입력 대기 때문에 감시가 멈추는 다른 문제가 생겼을 것이다.
- **순서:** 입력 확인 → 표시 → 통신 → 입력 확인. 통신이 끝나야 다음 입력 확인과 표시로 넘어간다.
- **예외:** 시험 서버에서 Ctrl+C는 대기 중에도 바로 끊겼다. 프로그램이 읽는 키가 아니라 운영체제 신호이기 때문이다. `quit` 명령은 통신 반환 뒤 처리된다. 실제 COM 포트의 Ctrl+C 동작은 미확인이다.

## 3. 동기로 충분한 상황과 비동기가 필요한 상황은 무엇인가?

**동기로 충분한 경우:** 통신이 정상이라 대기가 짧을 때다. 시험 서버의 정상 상태에서 키 읽기 지연은 동기 0.002~0.014초, 비동기 0.018~0.047초로 둘 다 짧았다. 다만 이 5건은 관측 직후, 즉 동기판이 통신 중이 아닐 때 누른 경우라 동기판에 유리한 표본이다. 정상 통신 중에 누르면 동기판은 그 통신 시간만큼 더 기다린다. 실제 PLC 읽기 한 번은 약 0.03초였으므로 이 지연도 작다. "비동기가 더 빠르다"로 결론 내릴 차이는 아니다. 또 응답을 기다리는 동안 처리할 다른 일이 없는 일회성 읽기·쓰기 도구도 동기로 충분하다. [PLC 정상 통신의 지연 수치로 확인]

**비동기가 필요한 경우:** 무응답처럼 대기가 길어져도 입력 접수, 상태 표시, 안내를 계속해야 할 때다. 이번 프로그램에서 2초 timeout 동안 동기판은 입력에 반응하지 않았고 대기 안내도 갱신하지 않았다. timeout이 길어지면 이 시간도 함께 길어진다.

**범위:** 이번 동기판의 한계는 "단일 흐름에서 통신 함수가 반환될 때까지 기다리는 구조"에서 나온다. timeout을 줄이면 지연은 줄지만 그만큼 정상 응답을 놓칠 위험이 커지고, 대기 중 처리가 불가능한 구조 자체는 그대로다.
